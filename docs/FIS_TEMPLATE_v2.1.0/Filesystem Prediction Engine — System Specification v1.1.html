Filesystem Prediction Engine — System Specification

POF 2828 | September 25, 2026 Status: Design Phase — Open for Multi-AI Review Parent Project: David-OS (D:\GitHub\David-OS) Layer: Prediction Harness

1. Problem Statement

Every file operation a user performs — copy, move, delete, rename, save, paste — is conditioned on context that repeats. Workflows are non-random. The question is whether a lightweight system can learn the topology of a user's filesystem behavior well enough to predict the next operation before the user performs it, and whether that prediction can be made reliable enough to act on.

This specification describes a system that:

  1. Monitors every file and folder operation across the user's filesystem in real time.
  2. Encodes those operations as weighted edges in a persistent graph where every file and folder is a node.
  3. Runs multiple competing prediction models against the same event stream to determine which architecture predicts best under which conditions.
  4. Surfaces predictions with calibrated confidence scores that reflect actual historical reliability, not raw model output.

The system is designed to be handed to multiple AI collaborators for independent implementation proposals. Each collaborator should address the four open questions in Section 6.

2. Architecture Overview

The system has four layers:

Layer 1: The Watcher

A daemon that hooks into the Windows filesystem notification system (ReadDirectoryChangesW or the Python watchdog library) and logs every event. The watcher is always-on, low-overhead, and writes to a local SQLite database.

Event schema (one row per operation):

event_id        TEXT    -- UUID
timestamp       REAL    -- Unix epoch, millisecond precision
event_type      TEXT    -- CREATE | MODIFY | MOVE | COPY | DELETE | RENAME | CLIPBOARD_COPY | CLIPBOARD_PASTE
source_path     TEXT    -- Full path of the source file/folder
dest_path       TEXT    -- Full path of the destination (for MOVE, COPY, RENAME; NULL otherwise)
file_extension  TEXT    -- e.g. ".md", ".html", ".pdf"
file_size       INT    -- Bytes (at time of event)
parent_dir      TEXT    -- Immediate parent directory of source
session_id      TEXT    -- Groups events by work session (gap > 30 min = new session)
day_of_week     INT    -- 0-6
hour_of_day     INT    -- 0-23
active_window   TEXT    -- Foreground application at time of event (via Win32 GetForegroundWindow)

Scope: All local drives the user works on. Exclude system directories (Windows, Program Files), hidden directories (.git internals, .obsidian cache), and any path matching a user-defined exclusion list. The FIS exclusion list already exists (.lake, .obsidian, .smart-env, .claudian, .trash) and should be inherited.

Clipboard integration: Hook the Win32 clipboard chain. When a file path hits the clipboard (copy operation in Explorer), log a CLIPBOARD_COPY event. When a paste occurs, log CLIPBOARD_PASTE with the destination. This is the primary trigger for real-time prediction: the moment something is copied, the system should already be ranking likely destinations.

Layer 2: The Node Graph

Every file and folder on the monitored filesystem is a node. The graph is persistent (SQLite or PostgreSQL) and survives reboots.

Node properties:

node_id         TEXT    -- Canonical full path (normalized)
node_type       TEXT    -- FILE | FOLDER
extension       TEXT    -- File extension (NULL for folders)
first_seen      REAL    -- Timestamp of first observed operation
last_seen       REAL    -- Timestamp of most recent operation
total_events    INT    -- Total operations involving this node

Edge properties:

Each node has a limited number of edges to other nodes (initially capped at 10 per node, expandable). Each edge has multiple weight channels — one per operation type:

source_node     TEXT    -- node_id
target_node     TEXT    -- node_id
weight_copy     REAL    -- Accumulated weight for COPY operations between these nodes
weight_move     REAL    -- Accumulated weight for MOVE operations
weight_rename   REAL    -- Accumulated weight for RENAME operations
weight_delete   REAL    -- Accumulated weight for DELETE proximity (co-deletion within session)
weight_coacccess REAL   -- Accumulated weight for co-access (touched in same session)
weight_sequential REAL  -- Accumulated weight for sequential access (B follows A within N seconds)
last_updated    REAL    -- Timestamp
decay_factor    REAL    -- Time-decay multiplier (recent events weighted higher)

Update rule (Hebbian): When an operation occurs between node A and node B:

  1. If an edge exists, increment the appropriate weight channel: w_new = w_old + learning_rate × recency_bonus
  2. If no edge exists and the node has fewer than max_edges, create one.
  3. If no edge exists and the node is at max_edges, replace the weakest edge only if the new signal exceeds a threshold.
  4. Apply time-decay to all edges on every update: w_decayed = w × decay_rate^(time_since_last_update)

The graph learns the user's usage topology — which files and folders are functionally related through behavior, regardless of where they sit in the directory hierarchy. Two files in completely different directory trees that are always touched together will develop strong edges.

Layer 3: The Prediction Models (Competing)

This is the core design question. Rather than choosing one prediction architecture, the system runs multiple models in parallel against the same event stream, in shadow mode, and measures which one predicts best under which conditions. Every model produces a prediction for every event. Every prediction is scored against what actually happens. The winner earns the right to surface predictions to the user.

The models to implement and compare (see Section 4 for full descriptions):

  1. First-order Markov chain (IPAM / Davison-Hirsh)
  2. Higher-order Markov chain (Jacobs-Blockeel variable-length)
  3. Context-enriched Markov (Korvemaker-Greiner: + time-of-day, day-of-week, error codes)
  4. LSTM sequence model
  5. Graph neural network over the node graph
  6. Hybrid: Markov verb prediction + graph noun prediction
  7. Frequency baseline (most common operation for this file/folder)
  8. Recency baseline (repeat the last operation on this file/folder)

Each model outputs:

predicted_event_type    TEXT    -- The operation it expects next
predicted_target_path   TEXT    -- The file/folder it expects to be involved
confidence              REAL   -- 0.0 to 1.0

Layer 4: The Meta-Predictor and Binary Gate

The meta-predictor watches each model's track record. For each model, in each context bucket (time-of-day, operation type, directory, session phase), it records:

  • How often the model's predictions were correct
  • How well-calibrated the model's confidence scores are (does "80% confident" actually mean right 80% of the time?)

This produces a reliability score per model per context. The final prediction is not just "Model X says MOVE to _OPUS_5 at 73% confidence" — it's "Model X says MOVE to _OPUS_5 at 73% confidence, AND Model X's 73% confidence in this context has historically been correct 81% of the time, giving a calibrated score of 0.59."

The binary gate collapses this to a yes/no decision for action. The formula:

gate_score = raw_confidence × historical_reliability_in_this_context

Above a user-set threshold (e.g., 0.85): the system can auto-suggest or auto-execute. Below threshold: silent logging only. The system watches and learns but doesn't surface anything.

The prediction history itself becomes training data for the meta-predictor — every prediction that was made, what actually happened, and the context in which it occurred. This is the self-correcting loop: the system learns when to trust itself.

3. Prior Art — Existing Approaches

The following are the documented approaches to user action prediction. Each one represents a different way to encode the information. The system should implement all of them behind a uniform interface and let measured performance decide the winner.

3.1 IPAM — Incremental Probabilistic Action Modeling

Source: Davison & Hirsh, "Predicting Sequences of User Actions," AAAI 1998.

Method: First-order Markov model. Stores conditional probabilities P(next_action | last_action). After each observation, updates:

  • P'(x|y) = α × P(x|y) + (1−α) for x = current observation, y = last observation
  • P'(x|y) = α × P(x|y) for all other x

α ≈ 0.8 recommended. Achieves ~38% online accuracy on UNIX command prediction across 77 users.

Strengths: Trivially simple. No training phase. Learns online. Tiny memory footprint. Immediate deployment.

Weaknesses: Single-step context window. Cannot learn multi-step patterns. No contextual features (time, file type, etc.).

Encoding: Flat probability table. Action vocabulary × Action vocabulary matrix.

3.2 Variable-Length Markov (Jacobs-Blockeel Extension)

Source: Jacobs & Blockeel, building on IPAM.

Method: Higher-order Markov. Dynamically extends context length when predictions are correct. If the sequence ...y₁y₀x was observed and the prediction for x was correct, stores longer context entries. Automatically finds the optimal context length per pattern.

Strengths: Captures multi-step sequences without fixed window size. Self-adjusting complexity.

Weaknesses: Database grows with context length. Can overfit to specific long sequences.

Encoding: Variable-length suffix tree of action sequences with associated probabilities.

3.3 Context-Enriched Markov (Korvemaker-Greiner)

Source: Korvemaker & Greiner, "Predicting UNIX Command Lines: Adjusting to User Patterns," 2000.

Method: Extends IPAM with contextual features: error code from previous command, day of week, time of day. Predicts complete commands, not just command stubs.

Strengths: Context awareness without deep learning. Time-of-day and day-of-week are cheap, powerful features for habitual workflows.

Weaknesses: Feature engineering is manual. Doesn't scale to many context dimensions.

Encoding: Conditional probability tables keyed by (last_action, context_features).

3.4 LSTM Sequence Model

Source: General deep learning literature. Relevant implementation: BlerinaRushiti/user-behavior-prediction-lstm (GitHub).

Method: Long Short-Term Memory neural network. Takes a sliding window of N previous events (typically 5-20), encodes each as a feature vector, and predicts the next event. Maintains a hidden state vector (128-512 floats) that carries compressed information across the sequence.

Strengths: Learns arbitrary-length temporal dependencies (in theory). Can discover patterns invisible to Markov models. Handles high-dimensional feature inputs natively.

Weaknesses: Requires training data (weeks of logged events). Computationally heavier. Hidden state is a lossy compression — it does NOT hold a map of the filesystem. Effective memory degrades beyond ~200-500 steps.

Encoding: Sequences of feature vectors. Each event encoded as [event_type_onehot, path_embedding, extension_onehot, hour, day_of_week, time_since_last_event].

3.5 Graph Neural Network over Node Graph

Source: General GNN literature applied to the node graph from Layer 2.

Method: The node graph (5,000 nodes, weighted edges) IS the model. When an event occurs, activate the source node. Propagation flows through weighted edges. The highest-activation destination nodes are the prediction. Hebbian weight updates after each event.

Strengths: Knows the full filesystem topology. Can predict destinations for files it hasn't seen in the recent sequence, as long as they have edges. Learns structural relationships (co-access, sequential access) that sequence models miss. Tiny memory footprint (~200KB for 25,000 edges).

Weaknesses: No temporal dynamics — doesn't know about ordering or timing without additional features. Requires the node graph to be pre-built and maintained.

Encoding: Sparse adjacency matrix with multi-channel edge weights.

3.6 Hybrid: Markov Verb + Graph Noun

Source: Proposed in this specification.

Method: The Markov chain predicts the operation type (the "verb" — copy, move, rename, delete). The graph network predicts the target file/folder (the "noun" — which node is the likely destination). The verb prediction selects which edge weight channel to use for the noun prediction.

Strengths: Decomposes the prediction into two simpler problems. Each component uses the architecture best suited to its sub-task.

Weaknesses: Assumes verb and noun are separable. In practice they may be entangled (the destination determines the operation type, not the other way around).

Encoding: Combined: Markov probability table for verbs + sparse graph for nouns.

3.7 Frequency Baseline

Method: For each file/folder, predict the most common operation ever performed on it. If file X has been MOVED 40 times and COPIED 10 times, always predict MOVE.

Strengths: Dead simple. Surprisingly hard to beat for highly habitual operations.

Weaknesses: No context sensitivity. No temporal dynamics.

Encoding: Per-node operation frequency counts.

3.8 Recency Baseline

Method: Predict that the next operation on a file will be the same as the last operation on that file.

Strengths: Captures short-term task repetition (when you're batch-renaming, the next operation is probably another rename).

Weaknesses: Fails at task transitions.

Encoding: Per-node last-operation register.

4. Encoding Structures — Uniform Comparison Framework

Every model above encodes information differently. To compare them fairly, each model must implement the same interface:

class PredictionModel:
    def name(self) -> str:
        """Model identifier."""

    def observe(self, event: FileEvent) -> None:
        """Ingest one event. Update internal state."""

    def predict(self, context: EventContext) -> Prediction:
        """Given current context, predict the next event."""

    def score(self, prediction: Prediction, actual: FileEvent) -> float:
        """Score a prediction against what actually happened. 0.0 = wrong, 1.0 = exact match."""

    def save_state(self, path: str) -> None:
        """Persist model state to disk."""

    def load_state(self, path: str) -> None:
        """Restore model state from disk."""

@dataclass
class FileEvent:
    event_id: str
    timestamp: float
    event_type: str          # CREATE | MODIFY | MOVE | COPY | DELETE | RENAME
    source_path: str
    dest_path: Optional[str]
    file_extension: str
    file_size: int
    parent_dir: str
    session_id: str
    day_of_week: int
    hour_of_day: int
    active_window: str

@dataclass
class Prediction:
    predicted_event_type: str
    predicted_target_path: str
    confidence: float        # 0.0 to 1.0
    model_name: str
    context_hash: str        # Identifies the context bucket for meta-prediction

@dataclass
class EventContext:
    last_n_events: List[FileEvent]   # Sliding window (configurable N)
    current_clipboard: Optional[str] # File path on clipboard, if any
    active_window: str
    hour_of_day: int
    day_of_week: int
    session_duration: float          # Seconds since session start
    session_event_count: int

Every model gets the same EventContext. Every model produces a Prediction in the same format. Every prediction is scored by the same score() function. The meta-predictor aggregates scores per model per context bucket.

Scoring function: Partial credit for partial matches.

  • Exact match (correct event_type AND correct target_path): 1.0
  • Correct event_type, wrong target_path: 0.5
  • Correct target_path, wrong event_type: 0.3
  • Both wrong: 0.0

5. Integration with David-OS

This system is a layer within the David-OS monorepo (D:\GitHub\David-OS) under the prediction harness. It should:

  • Share the uniform event schema already planned for FIS, behavior/prediction harness, and OS-State layers.
  • Inherit the FIS exclusion list for filesystem scanning.
  • Use the existing SQLite/PostgreSQL infrastructure on the NAS (192.168.1.177:2665) for persistent storage.
  • Respect the OS design principles: no background/resident programs unless explicitly appointed. The watcher daemon earns residency because filesystem events provably evaporate if not captured in real time. All other processing (model updates, meta-prediction, scoring) can run as batch jobs on the event log.
  • The prediction harness direction already states: "wire many prediction engines behind one uniform interface with shared statistics/telemetry, judge by measured hit-rate in shadow mode before letting any engine act." This specification is the detailed design for that direction.

6. Open Questions for Multi-AI Review

Each AI collaborator should address these independently:

Q1: System Architecture

How should this be structured as a system that can latch onto any process within two seconds of startup? What is the minimum daemon footprint? Should the watcher be a Windows service, a Python process, a compiled binary? How do we handle the cold-start problem (no historical data on first run)?

Q2: Recording with Minimum User Burden

The user should do nothing. The system should see the desktop, observe operations, and record them without any manual tagging, configuration, or intervention. What is the minimum viable recording setup that captures enough signal? Can we derive the clipboard state, active window, and session boundaries passively? What do we miss by going fully passive versus requiring occasional user input?

Q3: Encoding Comparison

Sections 3 and 4 describe eight candidate models and a uniform interface. Each collaborator should:

  • Propose the implementation for each model (libraries, data structures, training procedures).
  • Identify which models are likely to win under which conditions (sparse data vs. dense data, habitual workflows vs. exploratory workflows, small filesystem vs. large filesystem).
  • Propose any additional models not listed here that should be in the comparison.
  • Describe the meta-prediction architecture in detail: how exactly should the reliability calibration work? What context buckets should be used?

Q4: Metastasis Path

If the system works on filesystem events, how far can it extend into the rest of the operating system? The candidates for extension are:

  • Clipboard operations (already specified)
  • Window focus changes
  • Process launches
  • Browser tab activity
  • Keystrokes within applications (security boundary — discuss trade-offs)
  • Network activity correlation
  • Application-internal state (Obsidian, VS Code, etc.)

Each extension adds new node types and edge types to the same graph. What is the priority order? What are the diminishing returns? Where does the system hit a ceiling where more data does not improve prediction accuracy?

7. Success Criteria

The system succeeds if:

  1. Within 1 week of passive recording: At least one model exceeds the frequency baseline on event_type prediction.
  2. Within 1 month: At least one model achieves >60% accuracy on event_type prediction and >40% accuracy on combined event_type + target_path.
  3. Within 3 months: The meta-predictor's calibrated confidence scores are within 10% of actual reliability (when it says 80%, it's right 70-90% of the time).
  4. The system never acts without crossing the binary gate threshold. Silent logging and learning is the default. Action requires earned confidence.

9. Architectural Amendment: The Command Line as Primary Prediction Surface

Added September 25, 2026 — supersedes the passive-daemon-first approach in Sections 2-4.

The original architecture positions the prediction engine as a background daemon watching filesystem events. This amendment repositions it: the prediction engine lives inside the command line interpreter, sitting between intent and execution.

9.1 Why the Command Line

Every file operation — whether typed by the user, scripted, or issued by an LLM agent (Desktop Commander, Claude Code, bash) — passes through one choke point: the command line. This is the natural interception layer. The prediction engine doesn't watch events after they happen; it sees commands before they execute.

This is especially critical for LLM-driven operations. When an AI agent issues mv, cp, rm, or rename commands on the user's behalf, the prediction engine:

  1. Sees the command before execution.
  2. Checks it against learned patterns for that file/folder.
  3. If the command matches a high-confidence pattern: execute silently.
  4. If the command is unusual (low weight, unseen destination, anomalous operation type): pause and surface the anomaly.

This makes the prediction engine simultaneously a productivity tool (auto-completing likely destinations) and a safety layer (catching anomalous AI-issued commands before they touch the filesystem).

9.2 Shell Wrapper Architecture

The engine is implemented as a shell wrapper — a command interpreter that sits in front of the actual shell (PowerShell, cmd, bash, or any subprocess call). Every command passes through it.

[User / LLM Agent]
        │
        ▼
┌──────────────────────────┐
│   PREDICTION SHELL       │
│                          │
│  1. Parse incoming cmd   │
│  2. Identify operation   │
│     (move/copy/del/ren)  │
│  3. Query prediction     │
│     engine for this      │
│     source file/folder   │
│  4. Compare predicted    │
│     destination vs.      │
│     actual destination   │
│  5. Score confidence     │
│                          │
│  IF confidence > gate:   │
│     → execute + log      │
│  IF confidence = mid:    │
│     → show prediction,   │
│       ask confirm        │
│  IF anomaly detected:    │
│     → pause, flag,       │
│       require confirm    │
│                          │
│  6. Log result           │
│  7. Update weights       │
└──────────────────────────┘
        │
        ▼
   [Actual Shell Execution]
        │
        ▼
   [Filesystem]

9.3 Prediction Completion

When the user begins typing a command, the engine offers completions based on accumulated weights — not just path autocompletion (which any shell does), but behavioral completion:

  • User types move D:\DONT_TOUCH → engine completes with the most likely destination based on historical patterns for files in that directory, weighted by time-of-day and session context.
  • User types cp and pauses → engine shows the most likely source file based on what was recently modified, what's on the clipboard, and sequential-access patterns from the node graph.
  • User types del → engine shows files most likely to be deleted based on patterns (temp files, intermediate outputs, files that always get deleted after a processing step).

The completion is ranked by the gate_score (raw_confidence × historical_reliability). Only completions above a minimum threshold are shown.

9.4 LLM Safety Layer

When an LLM agent issues commands through the shell (Desktop Commander, Claude Code, any subprocess), the prediction engine applies a stricter gate:

  • Known pattern, high confidence: Execute. The LLM is doing what the user would do. No pause.
  • Known pattern, low confidence: Execute but log with a flag. Surface in the session summary.
  • Unknown pattern (file has never been moved to this destination, or operation type is novel for this file): Pause execution. Surface the command to the user with the message: "This operation has no precedent in your workflow history. Confirm?" This catches AI hallucinations, wrong paths, and accidental deletions before they happen.
  • Destructive operation (DELETE, overwrite) on a high-value node (many edges, high total_events): Always pause, regardless of confidence. High-value nodes are files the user touches frequently — they earned protection through usage, not manual configuration.

9.5 Integration with Existing AI Workflow

The prediction shell becomes the substrate that every AI collaborator's commands pass through. Whether it's Claude via Desktop Commander, Codex via terminal, or Gemini via a bridge script, the prediction engine sees and scores every command. Over time, it learns each AI's patterns too — not just the user's. It can flag when an AI agent's behavior deviates from its own historical patterns, which is a signal for session confusion, context loss, or adversarial injection.

9.6 Revised Open Question for Multi-AI Review

Q5: Command Shell Design. Each collaborator should propose:

  • The implementation language and framework for the shell wrapper (Python subprocess wrapper vs. PowerShell module vs. compiled interceptor).
  • How to handle commands that don't map cleanly to file operations (cd, ls, grep, etc.) — should the engine attempt to predict these too, or only intercept file-mutating commands?
  • How to minimize latency. The prediction lookup must be sub-100ms to avoid disrupting the user's flow. What data structures and caching strategies achieve this?
  • How to handle the cold start when the engine has no history. Should it run in pure-observation mode for a training period, or can it bootstrap from the existing FIS registry and vault structure?
  • How to surface predictions without being annoying. The engine should enhance the command line experience, not slow it down. What is the right UX for showing/hiding predictions?
